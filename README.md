# 双流乱序事件时间连接作业（Python + SQLite）

一个可重放、可续跑的后端事件时间连接作业。左侧与右侧乱序遥测流进入同一条
UTF-8 JSONL 操作日志；作业按事件时间把两侧配对，**绝不因为右侧数据尚未到达
就发布未匹配记录**，并且在对已接收的另一侧事件确定不能再配对之后，才按规则
回收其状态。

```
joinjob/
  model.py      纯校验与连接规则（JSON 解码、token/整数校验、排序键）
  engine.py     SQLite 持久化引擎：水位、活动事件、批次日志、消费位置
  __main__.py   命令行入口
tests/
  reference_model.py   独立全历史参考模型（逐批对拍用）
  fuzz.py              随机合法/非法日志生成器与差分工具
  test_join.py         46 个验收测试（unittest）
```

## 运行

```bash
# 初始化：左右各自给出非空分区标识集合
python3 -m joinjob init --db job.db --left-parts lp1,lp2 --right-parts rp1,rp2

# 消费日志（可反复执行；EOF 后可继续追加同一文件再跑）
python3 -m joinjob run --db job.db --input ops.jsonl --output batches.jsonl

# 查看持久化状态（水位、批次计数、活动事件数、消费偏移）
python3 -m joinjob status --db job.db
```

退出码：`0` 正常（含到达 EOF、含输入尾部尚未写完），`2` 遇到非法操作（已停在
前一个成功位置），`3` 输入/数据库不可用。

`run` 会先由已提交批次原子重写 `--output`，再追加本次新提交的批次，因此强退
后再次运行不会重复批次，输出文件也不会与数据库不一致。`--max-ops N` 可限量
消费，便于测试与分批调度。

## 输入格式

每行一个 JSON 对象（UTF-8，LF 结尾；也接受 `\r\n`）。操作序号 `seq` 从 1
连续递增：**日志位置即序号**，记录中的 `seq` 可省略；若给出则必须等于该位置。
仅以换行结束的整行记录才会被消费，末尾未写完的半行留待下一次运行。

事件（六个字段必须齐全且无多余字段）：

```json
{"side":"left","partition":"lp1","id":"l1","key":"k1","t":10,"value":"a"}
```

水位：

```json
{"side":"right","partition":"rp1","watermark":15}
```

契约校验（任一失败即非法操作，整条事务回滚，停在上一成功位置）：

| 项 | 规则 |
| --- | --- |
| `side` | `left` / `right` |
| `partition` / `id` / `key` | 非空 ASCII 字母数字及下划线（`[0-9A-Za-z_]+`） |
| `id` | 全局唯一（跨两侧、跨全历史；由持久去重账本保证） |
| `partition` | 必须属于初始化时该侧的分区集合 |
| `t` / `watermark` | 非布尔的有符号 64 位整数；`t >= 0`，`watermark >= -1` |
| `value` | 字符串或 `null` |
| 事件 `t` | 必须 **大于** 本侧本分区当前水位（等于即非法） |
| 水位 | 只能不减（等于合法） |
| JSON | 拒绝重复对象键、`NaN`/`Infinity`、非对象顶层值 |

`seq` 连续性是隐式的：每次提交固定写下一个序号，遇到非法行时该位置不会被
跳过，修复后的同一位置可继续消费。

## 语义

### 水位

* 分区水位初始 `-1`，只能单调不减；不推测空闲进度。
* 每侧有效水位 = 该侧 **全部分区** 水位的最小值。慢分区（哪怕一个停在 `-1`）
  会一直压住整侧进度，这正是“暂未收到右侧数据就不发布未匹配记录”的保障。
* 日志 EOF（临时读完）不推进任何水位，未决事件全部保留，等待追加续跑。

### 配对

* 同 key 且 `|left.t - right.t| <= 5`（含边界）即配对；`key` 不同不配对。
* 每对 `(left.id, right.id)` 恰好输出一次。重复样本（同一时刻多条、同值多条）
  是不同事件，各自参与配对；新右事件会与所有仍在窗口内、同 key 的已接收左事件
  （已匹配过的也包括）产生新的不同配对，反之亦然。
* 新事件到达时立即输出其与已接收另一侧事件的全部配对，同一批内按
  **左 id、右 id 的 ASCII 升序** 排序（右为 null 时排在该左事件的首位）。

### 未匹配裁决（`right = null`）

只有左事件会得到未匹配裁决，且必须同时满足：

1. 该左事件从未与任何右事件配对（即未被标记已匹配）；
2. 右侧有效水位 **达到** `left.t + 5`（`>=`，边界成立才输出）。

右侧未匹配事件 **永不输出**。裁决由“右事件”或“右水位”两种操作触发；触发时
该侧的有效水位一律按全分区最小值计算。左事件刚到达时若右侧有效水位已达
`t + 5`，则当批立即输出 null 行（它已不可能再配对）。

### 批次

每次操作产生一批，即使 `rows` 为空也保留。每行：

```json
{"seq":7,"op":{...原始操作...},"rows":[
  {"left":{"side":"left","partition":"lp1","id":"l1","key":"k","t":10,"value":"a"},
   "right":{"side":"right","partition":"rp1","id":"r1","key":"k","t":12,"value":"b"}}
]}
```

`op` 是规范化后的操作回显；事件对象总是六字段齐全（`value` 可为 null），
使用紧凑 JSON、字段顺序固定。批次日志是唯一真源，`--output` 只是它的导出。

## 状态回收（为什么不会保留全历史）

活动事件表只保存“仍可能配对”的事件：

* 左事件在右有效水位达到 `t + 5` 后即被删除（若从未匹配，删除前先输出 null）；
* 右事件在左有效水位达到 `t + 5` 后即被删除（右事件本身从不输出 null）。

正确性论证：任何未来的反侧事件 `t'` 必须严格大于其所在分区的水位，而该分区
水位不小于有效水位。因此当有效水位 `W >= t + 5` 时，未来事件必有
`t' > W >= t + 5`，即 `t' - t > 5`，不可能落入该事件的窗口。所以删除是安全的。
峰值状态量以“窗口内事件数”为界，与历史长度无关（测试用参考模型逐种子核对了
精确的存活事件数）。

唯一不随时间回收的索引是 `seen_ids`（全局唯一性去重账本）。它是校验索引而非
连接状态：状态回收针对的是“已不可能配对且已裁决”的**连接状态**，而 id 唯一性
必须覆盖全历史，否则重启后的重复 id 无法识别。若需要限制其体积，可换取更强
的前置约束（例如由上游保证 id 唯一），此时该表可删除。

## 持久化与故障恢复

* 每个操作一个 SQLite 事务，同时写入：状态变更、一个 `batches` 行、
  `next_seq`、`consumed_offset`（该行结束后的字节偏移）。三者原子提交。
* SQLite 使用 WAL + `synchronous=FULL`；提交前后的进程强退不产生半个操作。
* 启动时读取 `next_seq` 与 `consumed_offset`，从已消费字节偏移续读，不重放旧行。
* 输出文件每次运行由已提交批次重建（写入临时文件后 `os.replace`），随后以追加
  方式写入新批次；崩溃后即便输出文件落后，下次运行也会自愈为完整历史。
* 初始化在临时文件中建库、折叠 WAL 后 rename，避免半初始化文件。
* 非法操作：整个事务回滚，输出不追加，位置停在前一条成功操作之后。

python3 -m unittest discover -s tests -v

### 独立全历史模型对拍

`tests/reference_model.py` 保存全部历史，每批用全量扫描重新推导：配对、
null 裁决、排序与水位全部独立实现，只复用 `joinjob.model` 的常量与校验。它
还会给出“当前应存活的事件数”，供 `TestStateReclamation` 与差分测试断言引擎
回收得不多也不少。

### 手工强退复现

```bash
# 进程在 seq=8 提交前硬退出
JOINJOB_FAULT=before_commit:8 python3 -m joinjob run --db job.db --input ops.jsonl --output out.jsonl
# 直接再次运行即可：输出与从未故障时的基线完全相同
python3 -m joinjob run --db job.db --input ops.jsonl --output out.jsonl
python3 -m joinjob status --db job.db
```

`JOINJOB_FAULT=after_commit:N` 模拟提交后立刻断电（提交已落地、输出尚未写完），
同样依赖“输出由批次重建”自愈。

## 设计取舍

* **位置即序号**：不依赖输入自带 `seq`，杜绝“跳号”歧义；给出时只做一致性校验。
* **批次入库、输出导出**：批次日志是事实，文件是可再生视图，因此无需在两处
  维护 Exactly-Once。
* **右事件也参与删除**：右事件不输出 null，但删除条件仍用左有效水位，因为它
  只需能接收未来的左事件；左事件删除条件用右有效水位，两者对称。
* **全历史 id 账本**：见上文“状态回收”一节，这是唯一不完全随事件时间回收的
  结构；如需更严格的状态有界性，可将其改为上游保证并删除该表（引擎其余部分
  不受影响）。
